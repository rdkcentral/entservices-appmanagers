# RALF launch parity: AI1 and AI2

## Scope and terminology

**AI1** means the AppInfrastructure implementation in
[`ref/legacyappserviced`](../ref/legacyappserviced/); **AI2** means this
`entservices-appmanagers` checkout together with
[`ref/libpackage-sky`](../ref/libpackage-sky/) and
[`ref/entos-appmanagers`](../ref/entos-appmanagers/). This is a source-level
comparison, not evidence that any particular device has the required build
flags, packages, certificate roots, Dobby service, or effective configuration.
The [base-layer OCI deep dive](RALF_BASE_LAYER_OCI_BUNDLE_DEEP_DIVE.md) and
[base-free Dobby-spec deep dive](RALF_NO_BASE_LAYER_DOBBY_SPEC_DEEP_DIVE.md)
describe AI1's two launch paths. The current AI2
[launch scenarios](RALF_Launch_Scenarios_HLA.md) and
[package handoff](RALF_Package_Support_HLA.md) describe their counterparts.

AI1 normalizes RALF and ZIP packages into a common package model. AI2 registers
RALF packages in its shared PackageDatabase but materializes them through a
dedicated libpackage handler. It passes a dependency-first mount manifest
as `ralfPkgPath`, then chooses a traditional Dobby spec for recognized base-free
sets or an OCI bundle for base-backed sets. **RALF format alone does not require
an OCI bundle.** The table focuses on behavior available in AI1 that is
missing, narrower, or not yet demonstrated in AI2; it does not treat AI1's
first-dependency-only resolver as a target for regression.

## Already supported or intentionally different

| Area | AI2 evidence / qualification |
| --- | --- |
| Install and materialize RALF | AI2 detects bytes, verifies, installs, mounts read-only where possible and falls back to bounded extraction. [AI2 package flow](../ref/libpackage-sky/RALF_Package_Support_HLA.md#install-and-registration) |
| Base-backed OCI path | AI2 generates per-instance overlay `rootfs`/`upper`/`work`, a vendor GPU layer, OCI `config.json`, and base init + optional runtime + app + app `entryArgs`; it starts from the bundle and cleans up on failure/stop. This is **not** an outstanding wholesale OCI implementation. [builder](../RuntimeManager/ralf/RalfPackageBuilder.cpp#L40), [argv](../RuntimeManager/ralf/RalfOCIConfigGenerator.cpp#L617), [start](../RuntimeManager/RuntimeManagerImplementation.cpp#L966) |
| Base-free common paths | App-only RALF and runtime + app (including a ZIP runtime) select a traditional spec; a runtime with no executable uses the app executable and omits `/runtime`. [detector](../RuntimeManager/ralf/RalfSupport.cpp#L318), [mounts](../RuntimeManager/DobbySpecGenerator.cpp#L525) |
| Resolver improvements | AI2 recursively handles RALF dependencies and version constraints; AI1's ordinary package-set resolver only loads the first app/runtime dependency and does not resolve version constraints. Do not remove AI2's extra support when closing the ZIP-runtime graph gap. [AI1 resolver](../ref/legacyappserviced/RDK/AppManager/PackageManager/source/PackageManager.cpp#L377), [AI2 recursion](../ref/libpackage-sky/RalfPackageHandler.cpp#L1457) |
| Vendor and platform integration | AI2 has a generated vendor GPU layer and a separate EntOS platform-environment provider. Their presence does not imply all AI1 request-specific or package-specific variables are mapped. [vendor](../RuntimeManager/ralf/RalfVendorLayer.cpp#L22), [provider](../ref/entos-appmanagers/rdkappmanagers-sysconfig/DobbySpecGenerator.cpp#L710) |

## Recommended closure and verification

1. **Dependency correctness:** test RALF-runtime-to-base and decide whether
   ZIP-runtime-to-base is a new product feature; decide whether ZIP-app-to-RALF-runtime must work. Test lock order, base
   selection, rollback, final unlock and upgrades while locked.
2. **Base-free launch:** test app-only, RALF runtime, ZIP runtime, runtime with
   no executable, malformed entry points, and the exact `StartContainerFromDobbySpec`
   spec (argv, `/package` and `/runtime` binds, environment, permissions).
3. **OCI launch:** test RALF base + app, base + runtime + app, and mixed-format
   variants. Compare `process.args`, overlay lowerdir order, CA/vendor mounts,
   request variables and cleanup after Dobby startup failure. Test on a target
   with actual packages, Dobby and configured filesystem; source inspection
   does not establish device-level success.
4. **Product decisions:** explicitly accept or implement the optional
   secure-debug, metadata, runtime-switch and auxiliary-config differences.
   Keep AI2's recursive RALF dependency/version support and do not assume all
   fields in an AI1 traditional Dobby spec were ever forwarded from RALF
   metadata.

This report tracks source-level differences and the accompanying base-free
runtime fallback and RuntimeManager `ralfEnabled` launch switch. The focused
RALF test/source objects compile locally; the full RuntimeManager L0 executable
does not build against this host's installed Thunder interfaces. No device-level
parity test was run.
